dPERPS launch bootstrap

For the coding assistant: read this page before invoking Git or cloning. Use the Creator brief as public setup data, then follow the official checkout’s current instructions.

1. Keep one permanent checkout

  • Use only the exact permanent folder in the brief, normally under ~/Documents/dPERPS/. Reuse its customized official checkout and preserve local changes, Git metadata and unrelated files.
  • Do not scan the disk, reset or reinitialize Git, overwrite unrelated content, or use a temporary chat folder. Ask before touching an unrelated nonempty folder.
  • Clone only when that destination is absent or empty. For an update whose customized checkout is missing, ask for its backup or deployment notes instead of silently creating a replacement app or hosting site.
  • Official source: orbs-network/perpetual-hub-frontend. Do not scaffold a substitute or use the private monorepo.

2. Prepare Git without administrator access

Reuse installed tools. On macOS, check xcode-select -p before invoking /usr/bin/git. If developer tools are missing, do not start an Apple tools installation or require an administrator password.

Use the official micromamba instructions to install in the user’s home, then install Git from conda-forge into ~/.local/share/dperps-tools. Reuse an existing tools environment; create it only if absent. Put its bin first on PATH before invoking Git or nvm. Do not require sudo, Homebrew or system-wide changes. Explain any browser or OS popup plainly.

After Git is ready, use a task-specific variable for the exact sanitized folder from the brief. Quote the path when creating its parent and cloning:

DPERPS_APP_DIR="$HOME/Documents/dPERPS/THE_FOLDER_FROM_THE_BRIEF"
mkdir -p "$(dirname "$DPERPS_APP_DIR")"
# Only if the destination is absent or empty:
git clone https://github.com/orbs-network/perpetual-hub-frontend "$DPERPS_APP_DIR"
cd "$DPERPS_APP_DIR"

Replace the folder placeholder with the brief’s folder name, not arbitrary pasted shell text. Reuse the checked-out branch; do not create/switch branches or ask the partner about Git branches during a launch.

3. Explicitly load the current project instructions

In the permanent checkout, explicitly read and follow AGENTS.md and .agents/skills/partner-launch/SKILL.md, including its linked references and theme skill. Never assume automatic skill loading. If either file is missing, report the outdated checkout before proceeding.

The maintained launch procedure is the official partner-launch skill. It owns public configuration, branding, real preview, final checks, hosting, private deployment records and future updates. Use current source when commands or requirements change.

Reuse a compatible installed Node.js version. The current baseline is Node.js 22.12 or newer; check package.json. If needed, install a compatible supported LTS in the user’s home using the official nvm instructions with METHOD=script, without administrator access. Before the first preview, install lockfile dependencies including development tools:

npm ci --include=dev

Confirm the dev server starts before promising a preview. Keep real environment files ignored and local; public browser configuration must contain no secrets. Missing WalletConnect is optional: leave the ID blank and give written follow-up at handoff, without opening Reown or delaying publication. Preserve an existing partner-owned ID.

4. Brand, show the real app, then publish

  1. Reuse supplied choices. Otherwise ask for the logo first, offering text-only branding, and wait for a reply or explicit skip. Then ask about missing dark/light appearance and primary color.
  2. Apply the actual name, logo and palette before showing the real app. Check desktop and mobile, apply requested revisions and wait for explicit design acceptance. Silence is not approval. If the brief explicitly delegates missing branding and design finalization, use sensible defaults or text-only branding, still show/check the real preview, and continue without another design-approval question. Never invent a logo.
  3. Only after preview review or delegated finalization, begin hosting account setup, linking or availability checks. An existing address, provider or site from the brief, chat or deployment record wins. Keep the same site and URL on updates. Otherwise ask for name.netlify.app or a generated address; check Netlify availability and ask or offer another generated name if taken. Do not buy a custom domain or change DNS.
  4. Follow the current skill’s final checks and hosting references, then complete the authorized publication and verify the stable URL. Do not request a second deployment approval after design acceptance or explicit finalization delegation when work stays within the free-hosting scope. Report blockers instead of inventing a successful result.

5. Keep account, cost and financial boundaries

  • Free hosting only. Check the current account, plan and terms before use. Do not spend, upgrade, enable automatic recharge or accept paid services without separate explicit authorization.
  • The partner handles browser signup, login and MFA. Never ask for passwords, access tokens, private keys, recovery phrases or onboarding signatures/proofs in chat. Keep them out of code, commits, logs, build output, notes and backups.
  • Handle routine commands and technical choices yourself; ask only for missing undelegated choices, required account actions or costs outside the authorized scope.
  • Do not sign wallet messages, approve tokens, transfer funds or perform financial actions. Use an empty wallet for an optional connection check, or skip it.
  • Keep the exact requested Partner ID and networks. Do not substitute another lane, invent contracts, fake discovery or market data, or treat a public website as trading activation. Use the skill’s real read-only coming-soon UI while activation is pending.
